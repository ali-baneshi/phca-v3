## بخش ۱: تأییدِ ۵ فاز — همه واقعی و درست‌اند ✅

خبرِ خوب: هر ۵ مورد را مستقیم چک کردم و همه دقیقاً همان‌طور که گفته‌ای پیاده شده‌اند.

### ✅ Phase 1 — `_classify_action` برگشت به count-based + severity override
```python
if not violations: return CONTINUE
max_sev = max(v.severity for v in violations)
if max_sev > 0.8: return TERMINATE
count = len(violations)
if count >= 3: return TERMINATE
elif count >= 1: return INTERRUPT
else: return CONTINUE
```
این انتخابِ درستی است: به‌جای این‌که یک انتزاعِ ظریف (weighted-sum) بسازید که یک لبه‌ی پنهانِ شکننده دارد، به یک مدلِ ساده و اثبات‌پذیر برگشتید و فقط برای حالتِ واقعاً بحرانی (severity>۰.۸) یک override اضافه کردید. این تصمیمِ مهندسیِ درستی است — **سادگیِ قابلِ‌اثبات را به پیچیدگیِ ظریف اما شکننده ترجیح دادید.**

### ✅ Phase 2 — `severity` جهت‌نامتقارن (`abs()`)
```python
ratio = abs(self.measured - self.allowed) / max(self.allowed, 1e-9)
self.severity = float(np.clip(ratio / 5.0, 0.0, 1.0))
```
تست کردم با اعداد: `entropy=0.001, floor=0.01` → `ratio=0.9` → `severity=0.18`. دیگر صفر نیست. ✅

**یک نکته‌ی ریز برای آگاهی (نه باگ، صرفاً یک عدم‌تقارنِ ریاضی که ارزش دارد بدانید):**
چون آنتروپی همیشه `entropy ≥ 0` است، برای نقض‌های ENTROPY حداکثرِ ممکنِ `ratio` برابر با `(floor - 0)/floor = 1.0` است (وقتی آنتروپی دقیقاً صفر شود) → `severity` برای ENTROPY هیچ‌وقت نمی‌تواند از `1.0/5.0 = 0.2` بیشتر شود. در مقابل، برای TIME/MEM/ENERGY (که کفِ زیرین ندارند) `ratio` می‌تواند نامحدود بزرگ شود → `severity` می‌تواند به راحتی به ۱.۰ برسد.
**پیامد:** نقضِ ENTROPY به‌تنهایی *هرگز* نمی‌تواند از طریقِ مسیرِ «severity override» (`max_sev>0.8`) باعثِ TERMINATE فوری شود — فقط از طریقِ مسیرِ count-based (که با Phase 1 درست شده) می‌تواند. این با طراحیِ فعلی سازگار است (چون Phase 1 خودش این را جبران کرده)، ولی اگر روزی بخواهید override را برای انواعِ نقضِ دیگر هم تیون کنید، این عدم‌تقارن را یادتان باشد — یک collapseی کاملِ آنتروپی (بی‌نهایت overconfident) از نظرِ عددی «فقط با شدتِ ۰.۲» ثبت می‌شود، در حالی‌که از نظرِ مفهومی این بدترین حالتِ ممکن برای A3 است. پیشنهاد: اگر خواستید دقیق‌تر کنید، `severity` را برای ENTROPY با یک مقیاسِ جداگانه (مثلاً `ratio` بدونِ تقسیم بر ۵) حساب کنید، نه فرمولِ مشترک.

## بخش ۲: کاوشِ تازه در بخش‌های نیامده (طبقِ درخواستِ بررسیِ کامل)

### 🟡 NEW-02 — سیاستِ eviction در M3 (FIFO/oldest-first) با هدفِ anti-forgetting در تنش است
**شدت: بالقوه بالا، ولی در مقیاسِ فعلیِ بنچمارک غیرفعال (dormant)**

`memory/m3_episodic.py`, `_evict_if_needed()`:
```python
# Phase 1: evict consolidated episodes first
"... ORDER BY timestamp ASC LIMIT ?"   # قدیمی‌ترین‌ها اول
# Phase 2: evict unconsolidated only if still over limit
"... ORDER BY timestamp ASC LIMIT ?"   # باز هم قدیمی‌ترین‌ها اول
```
یعنی وقتی پایگاه‌داده از `max_episodes` (پیش‌فرض ۱۰٬۰۰۰) بگذرد، **همیشه اپیزودهای قدیمی‌تر اول حذف می‌شوند** — که در یک محیطِ continual-learning یعنی دقیقاً اپیزودهای **تسک‌های اولیه**. این مستقیماً با هدفِ `sample_prior_task_episodes()` در تضاد است، که تلاش می‌کند از **همه‌ی** تسک‌های قبلی (شاملِ اولین‌ها) نمونه بردارد تا فراموشی جلوگیری شود — اگر اپیزودهای تسکِ ۰ حذف شده باشند، دیگر چیزی برای replay از تسکِ ۰ نیست.

**چرا الان مشکل‌ساز نیست:** در بنچمارکِ L4 استاندارد (۱۰ تسک × ۸۰ سیکل = ۸۰۰ سیکل، که هر کدام احتمالاً یک اپیزود ذخیره می‌کنند) هرگز به سقفِ ۱۰٬۰۰۰ نمی‌رسیم — پس eviction اصلاً trigger نمی‌شود. یعنی **claim فعلیِ forgetting=۰٪ از این باگِ خاص متأثر نیست.**

**چرا مهم است که الان مستند شود:** این یک فرضِ نامرئی است («تعدادِ کل اپیزودها همیشه کوچک‌تر از max_episodes می‌ماند») که هیچ‌جا صریح تست یا مستند نشده. اگر کسی روزی بنچمارک را به تسک‌های بیشتر یا سیکل‌های بیشتر مقیاس دهد (که دقیقاً کاری است که برای «اثباتِ واقعیِ» ادعای continual-learning لازم است)، این فرض بی‌صدا می‌شکند و سیستم شروع به فراموشیِ واقعیِ تسک‌های اولیه می‌کند — دقیقاً پدیده‌ای که قرار است جلویش گرفته شود.

**راه‌حلِ پیشنهادی:** سیاستِ eviction باید task-aware باشد، نه فقط زمان‌آگاه. مثلاً:
```python
# به‌جای صرفاً "قدیمی‌ترین را حذف کن"، یک سهمیه‌ی حداقلی به‌ازای هر task_id نگه دار
# و فقط از تسک‌هایی که بیش از سهمیه‌شان اپیزود دارند اپیزود حذف کن.
```
یا حداقل، یک تستِ صریح اضافه کنید که رفتار را مستند کند: `test_eviction_does_not_starve_early_tasks_when_over_capacity` — که با `max_episodes` کوچک (مثلاً ۵۰) و ۱۰ تسک شبیه‌سازی کند و تأیید کند `count_for_task(0) > 0` بعد از eviction.

### 🟡 NEW-03 — `transfer_efficiency` در فرمولِ Φ-IQ مستقل نیست؛ باعثِ وزن‌دهیِ مضاعف می‌شود
**شدت: متوسط (به اعتبارِ آماریِ متریکِ محوریِ پروژه مربوط است)**

```python
result.transfer_efficiency = result.adaptation_speed * result.prediction_accuracy
result.phi_iq = compute_phi_iq(result, weights)
# DEFAULT_WEIGHTS: prediction_accuracy=0.20, adaptation_speed=0.20, transfer_efficiency=0.15, ...
```
`transfer_efficiency` یک متریکِ مستقلِ ششم نیست — **حاصل‌ضربِ دو متریکِ دیگری است که خودشان هم در همان فرمول با وزنِ کامل حساب شده‌اند.** یعنی وقتی `prediction_accuracy` و `adaptation_speed` هر دو بالا باشند، `transfer_efficiency` هم به‌طورِ خودکار بالا می‌رود — سه‌بارْ به همان سیگنالِ زیربنایی وزن داده می‌شود (یک‌بار مستقیم برای هرکدام + یک‌بار غیرمستقیم از طریقِ حاصل‌ضرب).

**پیامدِ عددی:** جمعِ وزنِ این سه ترم `0.20+0.20+0.15=0.55` است — یعنی **بیش از نیمیِ Φ-IQ** روی صرفاً دو سیگنالِ بنیادی (نه ۶ بُعدِ مستقل که اسمِ متریک ادعا می‌کند) سوار است. این یک ضعفِ کلاسیکِ طراحیِ composite index است (مشابهِ multicollinearity در آمار): وقتی یک زیرمعیار تابعی از بقیه است، شاخصِ نهایی دیگر واقعاً «۶ بعدِ مستقل» را نمی‌سنجد، فقط شکلِ ظاهریِ آن را دارد.

**راه‌حلِ پیشنهادی:** یا (الف) `transfer_efficiency` را از ترکیبِ خطی حذف کنید و جای آن یک اندازه‌گیریِ واقعاً مستقل بگذارید (مثلاً سرعتِ *نسبیِ* یادگیریِ تسکِ جدید نسبت‌به تسکِ اول، نه ضربِ دو متریکِ دیگر)، یا (ب) اگر می‌خواهید نگهش دارید، صریحاً در مستندات بنویسید «این یک متریکِ derived است، نه مستقل» و وزنش را طوری تنظیم کنید که double-counting را جبران کند (مثلاً کم‌کردنِ متناظر از وزنِ دو ترمِ پایه).

## بخش ۴: جمع‌بندیِ کلی تا این لحظه (سه دور)

روندِ کیفیِ کار مثبت است: دورِ اول شکاف‌های بنیادی را آشکار کرد (Attention مرده، MDIM دورزده)، دورِ دوم آن‌ها را درست حل کرد اما یک رگرسیونِ کوچک ساخت، دورِ سوم آن رگرسیون را هم با یک تصمیمِ مهندسیِ پخته (برگشت به سادگی) درست کرد. الگوی نگران‌کننده‌ای که در دورهای قبل دیدیم («معماریِ پیچیده در سناریوهای ارزیابی بی‌صدا کنار گذاشته می‌شود») در این دور تکرار نشد — یافته‌های تازه (M3 eviction، Φ-IQ redundancy) از جنسِ متفاوتی‌اند: **فرض‌های نامرئیِ مقیاس‌ناپذیر و ضعفِ آماریِ متریک، نه فریب یا bypass عمدی.**

**توصیه‌ی اولویت‌بندی‌شده برای دورِ بعد:**
1. F-06 core (eval-position confound) — چون قدیمی‌ترین و مهم‌ترین شکافِ حل‌نشده است.
2. NEW-02 (M3 eviction) — چون ارزان است (یک تست + یک تغییرِ کوچک در query) و از یک شکستِ بی‌صدا در آینده جلوگیری می‌کند.
3. F-04 (تکرارِ composition tree) — بهداشتِ کد، اولویتِ پایین‌تر.
4. NEW-03 (Φ-IQ redundancy) — نیازمندِ یک تصمیمِ آگاهانه درباره‌ی تعریفِ متریک، نه صرفاً کد.
