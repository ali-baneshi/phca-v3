## Lesson 1: Overview — Five Principles and the 12-Step Cycle

This lesson shows the blueprint of the entire building before entering into details. PHCA is built on five principles, each answering a fundamental need in designing a resource-constrained cognitive agent — and a 12-step cycle that connects these five principles in a fixed execution sequence.

**First Principle — Resource Constraints (A1):** No module in PHCA is allowed to assume it has unlimited resources. Each module has a ResourceBounds object with four numbers: B_time (maximum time per cycle, e.g., ASI only 5 ms and G' up to 20 ms), B_mem (maximum memory, e.g., G' up to 500 KB), B_energy (estimate based on number of computations), and entropy_floor (the entropy floor described in the third principle). A central monitor called RBTA checks each cycle whether anyone has exceeded their budget and, based on the number of violations, changes the actual behavior of the next cycle: zero violations means continue, one or two violations means INTERRUPT (the next cycle becomes more restricted), and three or more violations means TERMINATE (the agent is forced to perform a safe, simple action). The fundamental difference of this design from other systems is that these reactions are real and change the agent's behavior, not just log a warning.

**Second Principle — Temporal Causality (A2):** The execution order of modules is fixed and documented: first input sanitization, then memory writing, then prediction, then action selection, then action execution in the real world, and only then error computation and learning. Each module is only allowed to use the output of modules that executed before it. This principle may seem obvious, but in multi-module systems with internal states, subtle violations (such as using data from the previous cycle instead of the current one) easily occur. Interestingly, the developers created an experimental flag called `desync` that deliberately disrupts the order so they can verify that the violation detection system actually works.

**Third Principle — Incomplete Knowledge (A3):** The agent should never pretend its knowledge is complete. An "entropy floor" (e.g., 0.01) is defined, below which the agent's beliefs should never fall. This uncertainty is measured practically using the MC-Dropout technique: the same input is fed to the model several times, each time a random subset of neurons is dropped out, and the dispersion of outputs indicates the level of uncertainty. This method measures "the model's consistency with itself," not necessarily the model's correctness — a difference that will have major consequences later. RBTA checks this entropy floor like other budgets, although in practice this check is only really meaningful for one or two modules, and the rest have a constant symbolic value.

**Fourth Principle — Prediction as the Core (A4):** Every cycle, the agent must guess "if I do this, what will the world look like in the next step?" and this guess must actually affect its decision. The history of this principle in the project went through a full cycle: first, a geometric shortcut (like Google Maps) had replaced prediction without anyone noticing, then this was discovered and fixed, but when decision-making relied entirely on the model, it caused a disaster at larger scale (success rate fell below random), and ultimately the attempt to build a "confidence gate" (only use prediction when the model is confident) also failed because the confidence metric itself was unreliable and always showed 99%.

**Fifth Principle — Learning from Feedback (A5):** The difference between prediction and reality is the engine of learning. This learning chain has multiple layers: PEU measures the error, TSPL makes a minor adjustment (not on the main weights), the G' model itself adjusts the main weights with gradient descent, and the Attention layer is supposed to reflect the importance of different dimensions in the intensity of learning — although it was in this layer that a famous bug called "disconnected wire" was discovered: Attention computed the weights and wrote them onto the model, but the model never read them.

**The 12-Step Cycle** executes these five principles in a fixed sequence: (1) input sanitization by ASI, (2) writing to memory M1/M2, (3) prediction by G', (4) action selection, (5) action execution in the real world, (6) error computation by PEU, (7) learning by TSPL and the model itself, (8) motivational regulation (MDIM, APC, Attention, HPM) which runs concurrently with the previous steps, (9) safety check by RBTA, (10) logging, (11) consolidation, and (12) incrementing the counter and repeating. This cycle should not be confused with "project development phases" (which are historical concepts related to construction time).

A theme that repeats throughout these lessons: a beautiful design principle at the philosophical level may be only partially implemented at the implementation level. The difference between "existence of a component in the architecture" and "its actual effect on the final outcome" is only revealed by following the real data trace — actual code execution and observing actual behavior.

## Lesson 2: Memory and Consolidation

Memory in PHCA is not a single layer, but three layers with different functions, each working with its own mechanism. At the input of this system sits the ASI module (input sanitizer), the first guardian: it checks everything coming from the outside world for two types of "mathematical contamination" — NaN (invalid numbers like the result of zero divided by zero) and Inf (infinity). The presence of even one NaN in neural network computations acts like a drop of poison in a pool and can permanently corrupt the entire model. ASI might be the simplest module in the system, but this simplicity does not imply unimportance: a good gatekeeper at the entrance can prevent major disasters deep within the system. ASI itself is not exempt from the first principle and has only 5 ms of time and a small amount of memory.

After sanitization, it is **M1 (Sensory/Short-Term Memory)** 's turn: a FIFO buffer (queue) that holds the last 50 observations. It works simply and blindly — it discards the oldest to make room for the new. Alongside it is **M2 (Working Memory)**, which operates more intelligently: instead of deleting solely based on age, it uses a concept called **salience** to determine which memory is more important. This difference is critical — without M2, an important moment that is a bit old might be discarded right when it is still needed. Everything that the predictive model (G') and the motivational system (MDIM) need to understand the situation is supplied from these two layers.

**M3 (Episodic Memory)** is the third layer: a long-term memory stored on disk in an actual SQLite database. Unlike M1 and M2, which only hold recent moments, M3 retains complete memories for a long time. Its main role is to supply data for **Prioritized Experience Replay**: when the predictive model learns in stable mode, instead of learning from every immediate experience, it reviews batches of past memories — and memories that still have high prediction error (i.e., the model hasn't learned from them well) have a higher chance of being reviewed. This is exactly like memory replay during sleep that helps consolidate learning.

M3's design faced a subtle architectural contradiction: every memory has a capacity limit (e.g., 10,000 memories). The initial solution was to delete the "oldest," which seemed logical. But in an agent that must learn several different tasks consecutively (e.g., ten sequential tasks), the "oldest memories" are precisely the memories of the first tasks — meaning this seemingly neutral policy systematically destroys the memories of early tasks. This directly contradicted M3's goal (preventing forgetting). The final solution is **fair quotas** for each task: each task has a specific share of total capacity, and deletion only occurs from that task's own memories.

The final stage of the memory chain is **Consolidation**. Every few cycles, raw M3 memories are examined using **cosine similarity** to detect recurring patterns and convert them into **semantic facts** — more general and compact rules. These explicit facts are fed back to the motivational system. The difference between Consolidation and G' 's ordinary learning lies in the type of knowledge produced: G' stores implicit knowledge in neural network weights (not directly readable), while Consolidation produces explicit, retrievable knowledge — a difference similar to the unconscious skill of riding a bicycle versus conscious knowledge that can be articulated in words.

## Lesson 3: World Model and Prediction

G' — denoted mathematically as the transition function — is the beating heart of the entire PHCA architecture. It is a compact model of the world that learns "if I am in state X and perform this action, what will the next state be?" Almost every other module uses its output in some way: the motivational system uses prediction error to gauge confusion, RBTA uses its confidence for entropy checking, and action selection uses its predictions to score options. If G' is removed from the system, the rest collapses.

PHCA has three different implementations for G': Gaussian (classic statistical model assuming normal distribution), Discrete Graph (a map-like structure for discrete worlds), and MLP Neural Network (three layers, 128 neurons in each hidden layer, about 38,000 adjustable parameters — a very small number compared to modern networks but sufficient for this agent's small world). The MLP version is the primary implementation used in most formal experiments. Its exact architecture: input layer (takes current state + selected action), two hidden layers of 128 neurons with activation, and an output layer that predicts the next state.

**Confidence measurement** is done with MC-Dropout: the same input is fed to the model several times with random neuron dropout, and the dispersion of outputs indicates the level of uncertainty. A subtle and clever design choice: the designers **intentionally decided not to use direct comparison of prediction with current state for measuring confidence**. If they had done this, the model could learn a lazy trick: "always say nothing changes" — because this guess would usually be close to the current state and would get a high confidence score without actually having learned anything. This is an example of "reward system cheating."

**Two learning modes:** At the beginning (warm-up), the model learns one by one from each experience. After a while, it enters stable mode and instead of immediate learning, reviews small batches of past memories (from M3) — similar to memory replay during sleep for consolidation. This mechanism is combined with prioritized replay.

**Critical limitation that later had major consequences:** The MC-Dropout confidence metric only measures "the model's self-consistency in predicting one step," not the reliability of a chain of dozens of steps. A model can be very accurate and self-consistent in predicting the next single step, but when these small predictions are strung together to form a long path, small errors accumulate and the final result becomes completely wrong. In the lessons on action selection, we will see how this limitation became one of the project's greatest challenges.

Another architectural note: in practice, there is not always full equivalence between the three G' implementations. The MLP version is the one used in most formal experiments, while the "hybrid" version (all three together) is only active in specific experimental modes. Knowing this difference is important: when it is said "G' works like this," one must ask "which G'?"

## Lesson 4: Learning from Error

Learning in PHCA is a multi-layered chain that starts with error measurement and leads to gradual model adjustment. The first link in this chain is **PEU (Prediction Error Unit)** , which measures the difference between G' 's prediction and the real world state (after action execution). This error is **weighted by precision**: some dimensions are given more importance — if a dimension is usually variable, a small mistake in it matters less than when a usually stable dimension changes unexpectedly. PEU produces a single number, but this number is distributed throughout the system: to TSPL for learning, to MDIM for measuring confusion, and to final evaluation reports. Due to temporal causality, PEU always works one step behind G' — first prediction, then execution, then comparison.

**TSPL** is the second layer, about which there is a common but mistaken impression: its name is "learning" but it does not work on the main neural network weights. The main weights (the same 38,000 parameters) are learned by G' itself with standard gradient descent. TSPL only maintains a **small auxiliary vector** (the size of the state dimension, not the network size) that is added to the model's output as a final correction. This vector is adjusted with a simple delta rule (not full gradient descent) and has a safety valve: if the correction exceeds a threshold, it is automatically zeroed. This separation is logical — a large system (main network learning) and a smaller, faster system (TSPL) working together. But the architectural lesson here is: **when a module has a big, meaningful name (like "learning"), always ask how much of the actual work that name performs.** TSPL also plays a supporting role in protecting old knowledge: when the agent moves from one task to another, it can mark parts of its vector as protected so they do not change quickly in subsequent adjustments.

**Attention** is the third layer, which is supposed to regulate learning intensity based on the importance of different dimensions. It produces an "importance weight" for each dimension of the state, and this computation is sparse (focusing on a few important dimensions) and uses **Gumbel noise** to prevent premature locking onto a single choice.

Here lay one of the project's most important bugs — the **"disconnected wire" bug**. The chain was as follows: Attention computed the importance weights. These weights were written to a variable in G'. But when G' wanted to learn (perform gradient descent), it **did not read** these weights. That is, the computation was performed, numbers were produced, no error occurred — but the actual effect on learning was **zero**. Like a wire plugged into an outlet but whose other end is not connected to any device. This is the kind of bug that ordinary tests do not catch — the code runs, produces output, and gives no error. The only way to find it is to ask "is this variable actually read anywhere?" — tracing data from source to final destination, not just checking that the code runs without errors. Fortunately, this bug was later fixed, and now attention weights are actually multiplied into G' 's gradient computation during learning.

There is a simple and elegant test to verify learning functionality: if learning is turned off, the model weights should not change at all (relative change exactly zero). If it is on, a measurable change should be observed — a simple but decisive test.

## Lesson 5: Motivation and Regulation

If G' is the predictive brain, MDIM (Multi-Drive Intrinsic Motivation) is the decision-making heart — the system that determines "what is most important for the agent right now?" There are six intrinsic drives (needs), each representing one aspect of importance: reducing prediction error (I want to understand the world better), exploring new states (I want to see something new), conserving energy, and others. Each drive has a "deficit" number that, like hunger, increases over time. Each cycle, these six numbers are converted to probabilities via softmax, and one is selected as the current goal — with some randomness, not always the highest value.

MDIM's history is one of the most eventful parts of the project. In the initial version, when the agent had a specific external goal, a fixed rule bypassed the entire six-drive system and always selected only the error-reduction drive. Since almost all experimental scenarios have a specific goal, this meant **the six-drive system almost never actually worked in practice** — it only activated in rare goalless states. This was another "hidden shortcut," exactly like what we saw in action selection (Fourth Principle). Later, this fixed rule was removed, and now all six drives truly compete with each other, but this discovery itself shows how small, seemingly insignificant conditions can neutralize the entire philosophy of a system in practice.

**APC (Adaptive Parameter Control)** is the next layer — like a thermostat that, instead of temperature, controls the instability of prediction error. It uses the classic PID technique used in industry (from furnace regulation to autonomous vehicles): three components — "how far am I from the ideal state right now" (P), "how much have I cumulatively deviated over time" (I), and "how fast am I moving toward or away from the ideal" (D). APC uses this combination to adjust parameters such as learning rate and decision thresholds. If error is very unstable (the environment is changing rapidly), APC adjusts parameters so the system behaves more cautiously. Without this layer, the system would have to work with fixed numbers, which are not optimal for changing environments.

**HPM (Hierarchical Procedural Memory)** builds a tree structure of cognitive cycle stages. It has two composition types: SEQUENCE, where total time = sum of times of all parts, and PARALLEL, where total time = maximum time among parallel parts. An interesting point: in parallel mode, **energy always adds up** even if time overlaps — because two concurrent paths both consume energy. This distinction (time = max in parallel, energy = always sum) is implemented correctly according to a formal theorem in the project documentation. HPM's output is given to RBTA to determine whether the cycle exceeds the budget.

In HPM's history, there was a recurring problem: the cycle's tree structure was manually rewritten separately in several different places in the code — one version for lighter mode and another for the final check. This classic software engineering risk (copying logic in multiple places) was later fixed by consolidating everything into a single function.

## Lesson 6: Safety and Resource Monitoring

The safety monitor RBTA (Resource-Bounded Turing Administrator) is the heart of PHCA's safety system. Each cycle, after all modules have executed, RBTA checks whether anyone has exceeded their budget. There are four types of budget: B_time (time), B_mem (memory), B_energy (computational energy), and entropy_floor. The reaction has three levels: zero violations = continue, one or two violations = INTERRUPT (next cycle is more restricted), three or more violations or one very severe violation = TERMINATE (agent forced into a safe, simple action like standing still).

The story of computing "violation severity" is one of the most instructive examples of this project. The first version simply counted violations — simple but with a logical flaw: a minor violation (one millisecond over the limit) had the same weight as a catastrophic violation (a thousand times the limit). The second version tried to be more precise: instead of simple counting, it computed a "severity" between zero and one for each violation. But here a subtle bug was introduced: **the severity formula assumed that violation always means "the number exceeded the upper limit" (like time or memory). But entropy violation is the opposite — it means the number crossed a lower limit. Because the formula did not account for this reverse direction, every entropy violation always received a severity of zero.** That is, the monitor was completely blind to one type of risk — the agent's uncertainty dropping too low. This bug was later found through a direct test: "when only an entropy violation occurs, does the system respond correctly?"

The final version is a combination of both approaches: simple counting (reliable) plus an exception for truly catastrophic cases. The architectural lesson of this story is deep: **when you want to make a simple system more precise, you must ensure the new version still covers all the cases the old version covered.** Here, the attempt to become more precise (from counting to weighted severity) completely ignored one type of violation — and the solution was not to abandon precision, but to write a test that directly checks that specific scenario.

Another key point: this monitor has real power — when it says TERMINATE, the agent's behavior actually changes. This is its superiority over systems that just print warnings. But this power has two edges: if RBTA itself (or the budget settings) is wrong, it can silently paralyze the agent — and exactly this happened in one of the project's most critical moments, where G' 's time budget was not updated as the network grew, and the agent was forced into immobility 99% of the time, without anyone realizing where the problem was.

## Lesson 7: Decision-Making in Discrete Worlds

This lesson addresses the most important and eventful part of the project: action selection in GridWorld — a grid-based environment with five actions (up, down, left, right, stay). Two approaches stand in opposition: the geometric/classical approach (memoryless pathfinding algorithm, reliable, computes from scratch every time) and the prediction-driven approach (PHCA's philosophical goal that every decision must pass through the learned G' model).

This confrontation has four stages. **Stage One — Hidden Shortcut:** In the initial version, when the goal was clear and the model seemed confident enough, the system completely used the geometric approach and never consulted G'. The Fourth Principle was violated in practice, but since a number always came out from somewhere, no one noticed. **Stage Two — Correction:** This shortcut was discovered and removed. Every action had to go through G'. On a small grid (5×5), this worked — even better than before. **Stage Three — Disaster at Scale:** When they tried the same method on a larger grid (10×10), the success rate plummeted to 0.03% — worse than even a completely random agent. **Stage Four — Confidence Gate and Its Failure:** To solve the problem, they built a "confidence gate": if the model was confident, use its prediction; if not, revert to the geometric method. But the gate did not work because the model always claimed 99% confidence — even when it was completely wrong. The reason was that the confidence metric only measured "am I right in predicting one small step?" (which is an easy task), not "does a chain of dozens of steps actually reach the destination?" (which is much harder).

**Current status:** The current default for discrete worlds is a return to the pure geometric method — but this time fully transparent and documented, not hidden. The learned model still trains and predicts (for other purposes like entropy measurement), but it does not have the primary role in direct action selection.

But this was not the end of the story. After weeks more work, a surprising discovery was made: **that 0.03% number was never about what we thought it was.** G' 's time budget was a fixed number that did not change as the network grew, while it should have scaled proportionally with network size. The result: in 99% of cycles, this budget was exceeded and RBTA forced the agent to stand still — regardless of which decision method was being executed. When the budget was fixed, the 0.03% number turned into 77.8%! The geometric method at 97.1% was still better, but there was no longer a disaster — just a notable difference. That disaster had nothing to do with the learned model; RBTA — the very monitor whose real power was the system's strength — had paralyzed the agent with its incorrect settings. The prediction-driven approach was an innocent defendant accused of a crime committed by someone else.

The final four-factor experiment (controlling world size, resource violation rate, limited vision, and sufficient samples) revealed a more nuanced picture: in a small world, even the geometric method itself was sometimes no better than a simple greedy rule. In a large world, geometry was more successful but the resource violation rate was still relatively high. The prediction-driven method with gate was not better than geometry in any case. In the limited-vision world, both methods performed exactly the same. The final decision: the default remains geometry, but with a clearly documented condition stating "if these conditions hold, this decision will change" — a golden pattern for scientific decision-making.

## Lesson 8: Decision-Making in Continuous Worlds

Unlike the discrete world with five limited options, in continuous worlds (such as controlling a pendulum or a robotic arm) there are infinite options — every decimal number between negative two and positive two. Not all can be evaluated. PHCA uses **MPC (Model Predictive Control)** : instead of evaluating all options, 8 random samples are selected from the possible range, for each one G' is asked "if I do this, where will I be next?", and the option that best aligns with the goal is selected. Each option's score is a combination of model confidence, prediction-goal alignment, and a small additional weight to encourage occasional exploration.

Why did the same problem as the discrete world not arise here? Two major reasons: **First** — in this world, no geometric shortcut was ever designed from day one. The path was always forced to go through G', without exception. **Second and more importantly** — when this path was tested with a long experiment (a thousand consecutive steps), the result was genuinely good. In one experiment, prediction error decreased by about 89%, no resource violations occurred, and no invalid numbers (NaN or Inf) were found. That is, unlike the discrete world, the claim was confirmed by actual experiment.

**Deep comparison of these two worlds** provides an important architectural insight: the same design philosophy can work perfectly in one domain and fail in another — not because the philosophy is wrong, but because of the difference in the nature of the problem. In physical control (pendulum, arm), each small step shows its effect almost immediately, and short-term prediction is aligned with control quality. In navigating a large grid, dozens of correct steps must be strung together to get the correct final result — and error accumulation over long paths can be catastrophic, even when each individual step seems reasonable on its own. This difference of short-horizon versus long-horizon is the root cause of the different behavior in the two worlds.

PHCA uses three environments in the MuJoCo simulator: **Inverted Pendulum** (holding a pole upright with a motor), **Reacher** (a two-joint arm whose tip must reach a target), and **Cartpole** (a cart that balances a pole — this one, unlike the other two, is discrete, only left or right). GridWorld is also configurable from 5×5 to 20×20. The diversity of test environments played a critical role in discovering the system's limitations: the long-horizon navigation problem was not visible at all in a 5×5 grid and only became apparent when scaling up to 10×10. Environmental diversity is itself a discovery tool, not just a showcase.

## Lesson 9: Evaluation and Measurement

PHCA has a multi-layered evaluation system ranging from a composite metric to four levels of testing and a full observatory.

**Φ-IQ (Phi-IQ)** is a single number between zero and one that combines five components: prediction accuracy (closeness of predictions to reality), adaptation speed (reaction to changing conditions), goal complexity (ability to pursue diverse goals), resource efficiency (performance within budget), and failure rate (with negative sign). A subtle error in Φ-IQ was discovered: a sixth component called "transfer efficiency" had been added that was not independent — it was exactly equal to the product of prediction accuracy and adaptation speed, two components already in the formula. This meant these two components were effectively double-counted. The sixth component was removed (though it is still reported as a side diagnostic number).

**Four evaluation levels L0 to L3:** L0 (Static Prediction) — the simplest test, the environment remains fixed and only G' 's accuracy in predicting simple patterns is checked. L1 (Reactive Control) — the agent must actively move, and both prediction accuracy and action diversity are measured. L2 (Goal Pursuit) — a specific goal in a maze full of obstacles, and the goal-reaching rate is measured (this is where the challenges from the previous lesson appeared). L3 (Spontaneous Exploration) — no mandatory goal exists, and it measures whether the six-drive system actually uses the diversity of drives. A subtle problem existed in L3: even this test, which was supposed to be "free of goal pressure," had an indirect goal in its initial setup, so it still fell under MDIM's old limitation. This was fixed.

**L4 — Continual Learning and Forgetting:** The agent learns ten different tasks consecutively and is then checked to see if it remembers the first tasks. The initial result was striking: **the forgetting rate was exactly zero.** But there were two problems with this measurement. The first problem: the evaluation started from exactly the same point where training had ended — meaning the agent started right next to the goal, making the test artificially too easy (this was later fixed). The second problem was deeper: because in the current configuration the final decision comes from the memoryless geometric method, and a memoryless method by definition cannot forget (it calculates the path from scratch every time), the "zero forgetting" number measures more the power of a classic pathfinding algorithm than the true resilience of learned memory. An important lesson: **a striking number (like zero percent) should always spark curiosity, not just joy.**

**Causal test (comparison with simple methods):** PHCA is compared with three rivals: random (baseline), observed greedy (simple "move toward the goal" rule with the same information as PHCA), and full search (optimal map-aware algorithm, for reference only). The result with sufficient runs: **in several scenarios, PHCA did not even outperform the simple greedy rule.** This does not mean the model is worthless — it works excellently in continuous worlds — but in grid worlds, there is no measurable advantage between the complex system and a simple rule. This is the most honest test to answer the question "is this complexity really worth it?"

**Cognitive Observatory** records every detail of the agent each cycle: what it saw, what it predicted, which drive won, how confident it was, whether RBTA detected any violations. It has two modes: live (graphical dashboard) and replay (moment-by-moment review after execution). A large portion of the project's deepest findings — including the discovery of 99% confidence and the geometric shortcut — were obtained through this tool. Investment in "the ability to see inside the system" is as important as the system itself.

## Lesson 10: The Full Story — Discoveries, Lessons, and Future Path

This lesson is the final review of the project's exploratory journey, from documentation culture to the biggest diagnostic mistakes and the future roadmap.

**Documentation culture:** PHCA has a massive document (hundreds of numbered entries) where every design decision — whether accepted or rejected — is recorded with its rationale. Recording rejected decisions is as important as recording accepted ones, because it prevents rework in the future. If someone asks a year later "why didn't we use that simpler method?" and the answer is not recorded, they will try the same path again and hit the same wall. However, a subtle gap was seen between internal technical documents (very honest) and external summaries (slightly more optimistic).

**Three levels of findings:**
Level one — simple bugs: such as the severity formula in RBTA that always gave zero for entropy violations. These were quickly found and fixed.
Level two — architectural gaps: such as Attention that was computed but not read (disconnected wire), or MDIM that was bypassed (hidden shortcut). The code did exactly what was written, but what was written was distant from what was claimed.
Level three — open scientific questions: such as "does the learned model have an advantage over a simple rule in grid worlds?" These require more experimentation, not a single line of corrective code.
A recurring pattern throughout the project: many times a component seemed beautiful and logical at the design level — but when the real data trace was followed, either the connection was broken, or a hidden shortcut had replaced the main path.

**The confidence gate failure mechanism:** To understand why it failed, the system itself was run directly and two numbers were recorded over 200 cycles: model confidence and gate threshold. Confidence from cycle one to cycle two hundred remained almost always around 99% — regardless of whether the agent reached the goal (which in that experiment it almost never did). Worse, every 100 cycles a benchmark test was run that, if it reported "high accuracy," would raise (tighten) the gate threshold. Since the benchmark also always reported "99% accuracy," the threshold rose from 0.65 to 0.875 in just 200 cycles. That is, the gate became tighter as it went forward, not looser. Root cause: both confidence and the benchmark only measured "one-step accuracy," not the reliability of long decision chains.

**The Big Misdiagnosis (Lesson 32):** The 0.03% number, which had been the basis for several major decisions (return to geometry, building the confidence gate, philosophical redefinition), was never about the quality of prediction-driven decision-making. A wrong setting in RBTA — G' 's time budget that was not updated as the network grew — kept the agent immobile in 99% of cycles. When the budget was fixed and the same experiment was re-run, 0.03% turned into 77.8%. The geometric method at 97.1% was still better, but the causal story had completely changed: it was no longer a "prediction-driven decision-making disaster," but rather "a safety monitor with wrong settings had paralyzed the agent." Even the previous deep analysis (discovery of the confidence metric's inaccuracy in Lesson 31) had not seen this layer because it had not recorded the resource violation rate. The big lesson: **when a key number differs between two states, before building a causal story about the decision-making layer, first check the execution layer and constraints.**

**The final four-factor experiment (Lesson 33):** After that discovery, instead of a hasty decision, a complete experiment with four questions was designed: is the result the same at all sizes? Is the resource violation rate fooling us again? Does it hold in a limited-vision world? Is the number of trials sufficient? Result: small world — geometry itself sometimes failed. Large world — geometry more successful but resource violation rate high. Prediction-driven method with gate — not better than geometry in any case. Limited vision — both methods identical. The final decision was to remain with geometry, but with a **clear criterion for reversibility** written down: "this decision will change if these conditions hold" — a golden pattern of commitment to flexibility in the face of contrary evidence.

**Nightly system flaw (Lesson 34):** The automated nightly review system had a seven-step list that all ran sequentially. Step six — the same goal-pursuit test that showed weakness in small worlds — would error with default settings. Since the steps were sequential, as soon as step six was reached, the entire chain stopped and step seven never executed. The likely result: a tool that was supposed to check the system's health every night had probably been silently failing for a while — not because someone made a mistake, but because a new finding (geometry's weakness in small worlds) had not yet been propagated to the automated tooling layer. A smaller finding was also discovered in this review: the main documentation table contained a row for ASI tests that were supposed to be viewed separately, but no such separate test existed — another gap between documentation and reality.

**Final picture of the building (Lesson 35):** The foundation (five principles) is solid. The skeleton (12-step cycle and all rooms) is in place — some rooms built exactly according to the blueprint (HPM, final RBTA), some had their wiring disconnected and have since been reconnected (Attention, MDIM). The exterior is perfect in continuous worlds but still has scaffolding in discrete worlds. The inspection system (evaluation and observatory) is very strong but itself also needs inspection.

**Open roadmap (four remaining scaffolds):** (1) Real confidence gate — there is still no metric for "is this prediction reliable in a long chain?" (2) Navigation weakness in small worlds — even geometry is no better than a simple greedy rule. (3) Health of the monitoring system itself — must ensure the nightly review runs completely without premature termination. (4) Multi-module entropy — still only a small fraction of modules are actually under entropy floor monitoring.

**The biggest lesson of the entire course:** No finding, no matter how definitive it seems, is the end of the story until it has been verified from multiple different angles. The 0.03% number seemed definitive. The confidence metric analysis in Lesson 31 had found the root of the problem. Both were correct in their own right, but neither was complete until the resource monitor layer was also checked. This project is exactly what it claims to be: a research sample, not a final product. Its real value lies in its honest documentation culture that allowed everyone to open these complex layers one by one. An imperfect system that honestly acknowledges its imperfection is more trustworthy than a system that claims completeness without actually being so. This building is not yet complete. But its blueprint is clear, its scaffolds are visible, and its engineers honestly document every finding they make — and for a research project, perhaps that is exactly what it should be.
